# vara 대시보드와 기존 AINS 업무 통합

## 통합 범위

- ctas main 시작점: `8762e56`
- 반영한 vara: `2430f3186349dc6cae213d3a65389d34c575894c`
- 기존 플랫폼: AINS 0.1.0, 26개 DB 마이그레이션과 8단계 워크플로우 프리뷰

vara의 커밋 이력·기획 문서·화면 구조와 기존 플랫폼 소스를 함께 보존한다. 실제 대시보드는 기존 프로젝트 원장을 조회하고 해당 프로젝트의 업무 화면으로 연결한다. 별도 DB를 만들거나 기존 프로젝트·문서를 다시 등록하는 방식이 아니다. 운영 시 기존 앱 서비스의 DB 연결과 설정을 유지해야 한다.

## 화면 경로

| 경로 | 역할 |
| --- | --- |
| `/` | 기존 인증된 작업실: 프로젝트 생성, 계약·기획, 문서, Main Context, 실행·검수 등 |
| `/dashboard/` | 실제 업무 대시보드: 기존 프로젝트의 문서·검토·작업·질문·활동 요약 |
| `/dashboard/example/` | vara의 예시 대시보드 진입점 |
| `/dashboard/alerts/`, `/dashboard/projects/.../` | 예시 알림함·프로젝트 상세·설정 화면 |
| `/preview` | 기존 8단계 전체 워크플로우 체험 |

실제 대시보드의 프로젝트 목록은 현재 계정의 접근 권한으로 조회한다. 문서 등록·계약 문서 작성·Context 검토·기능별 작업·AI 구현·질문 관리 등은 선택한 프로젝트의 기존 작업실로 이어진다. 조회 중·비로그인·빈 프로젝트·권한 없음·조회 실패를 구분하며, 오류가 발생해도 예시 데이터를 실제 자료처럼 표시하지 않는다.

## 실제 데이터 조회

`GET /api/projects/:p/dashboard`는 기존 세션 인증과 프로젝트 membership 검사 뒤에서 실행된다. 열람 권한도 조회할 수 있으며, 회원이 아니거나 없는 프로젝트는 404를 반환한다. 요약 쿼리에서도 membership을 다시 검사한다.

한 번의 읽기 전용 SELECT로 동일한 DB 스냅샷의 집계와 최근 목록을 반환한다. 집계는 목록 제한과 무관한 전체 개수이며, 각 목록은 최대 6개다. 원문 본문·AI 입력·자격증명은 요약 응답에 포함하지 않는다. DB 쓰기·AI 호출·메시지 발송을 실행하지 않으며, 새 마이그레이션도 추가하지 않는다.

| 집계 | 대상 |
| --- | --- |
| `documents`, `revisions` | 프로젝트의 전체 문서·리비전 |
| `pending_reviews` | `needs_review`, `no_change`인 변경 검토 |
| `failed_jobs` | `failed`, `uncertain`인 문서 처리 작업 |
| `context_entries` | 승인되어 저장된 전체 Context 기록 |
| `context_pending` | `pending`인 Context 후보 |
| `open_tasks` | `done`을 제외한 기능별 작업 |
| `open_questions` | `draft`, `waiting`, `answered_pending`인 질문 |
| `commercial_documents` | 전체 제안서·견적서·계약서 |

목록은 최근 문서, 검토할 변경 문서, 완료 전 작업, 미해결 질문, 활동 이력이다. 문서 상태는 최신 리비전의 처리 상태이며 리비전이 없으면 `draft`다. 문서의 `updated_at`은 최신 리비전 등록일, 검토의 `updated_at`은 검토 등록일이다. 작업의 `due_at`은 기존 `due_on`의 `YYYY-MM-DD` 날짜이고 질문의 `due_at`은 타임스탬프다. 기한이 없으면 `null`이다.

## 같은 프로젝트에서 업무 이어가기

작업실은 `?project=...&tab=...`을 읽어 해당 프로젝트와 업무 화면을 연다. `action=upload`는 권한과 프로젝트 자료 조회가 완료된 뒤 등록창을, `action=new-project`는 프로젝트 생성창을 연다. 창을 여는 동작만으로 자료나 프로젝트가 저장되지는 않는다.

대시보드로 돌아갈 때도 현재 프로젝트 ID를 유지한다. 명시한 프로젝트가 없거나 권한이 없으면 다른 프로젝트를 대신 선택하지 않는다. 기존의 미저장 내용 확인 절차를 유지하며, 프로젝트 목록과 권한을 확인하기 전에는 해당 프로젝트의 상세 현황을 요청하지 않는다.

Google 로그인은 콜백이 `/`로 돌아오므로 로그인 직전의 허용된 프로젝트·탭·동작만 `sessionStorage`에 최대 15분간 보관해 한 번 복구한다. 외부 URL로 이동하는 값은 저장하지 않는다. 브라우저 저장소가 차단된 경우에도 로그인은 가능하지만 OAuth 목적지 복구는 생략된다. 이메일 재로그인 후에는 접근 가능한 명시적 프로젝트를 다시 선택한다.

## 예시 화면의 범위

`/dashboard/example/`에서 이어지는 알림함·자료 넣기·결정 기록·메일 초안·설정은 vara의 mock 데이터 기반 화면이다. 예시 안내를 표시하며 실제 저장·AI 처리·메일 발송은 하지 않는다. 예시 입력과 처리 상태는 새로고침하면 초기화된다. `/preview`의 기존 전체 흐름 체험도 그대로 유지한다.

## 빌드와 배포 구조

Next 대시보드는 `basePath: '/dashboard'`와 정적 내보내기를 사용한다. 루트 빌드는 Vite 작업실과 Next 결과를 `dist/`에 합친다. Express가 `/dashboard` 아래의 정적 경로를 먼저 처리하고 실제 데이터 요청은 동일 출처의 기존 API로 전달한다. 별도의 운영 Next 서버가 필요하지 않다.

Next 인라인 초기화 스크립트는 내보낸 HTML의 SHA-256 해시로 CSP에 허용한다. 기존 작업실·API의 스크립트 정책은 유지한다. 미등록 대시보드 경로는 404를 반환하며 작업실로 잘못 대체하지 않는다. 소스 파일을 쓰는 개발용 CTDS 온보딩은 정적 대시보드에서 실행하지 않는다.

Railway는 기존 앱 서비스·PostgreSQL·서비스 변수를 유지한 상태에서 루트 Docker 이미지를 갱신한다. GitHub 반영과 운영 배포 완료는 별개다. 이 문서는 운영 배포 완료나 실제 Nora 실행 검증을 의미하지 않는다.

## 검증

실제 데이터 연결을 위해 다음 항목을 검증한다.

- 기존 데이터의 정확한 집계와 최근 6개 제한, 프로젝트 간 격리, 열람 권한, 권한 회수
- 원문·세션 정보 비노출과 읽기 전용 트랜잭션에서의 요약 조회
- 같은 프로젝트로 이동, 유효한 프로젝트의 재로그인 복구, 잘못된 목적지 차단
- Google 로그인 목적지의 일회성·만료 처리와 브라우저 저장소 차단 시 로그인 유지
- 기존 인증·권한·CSRF·원문 다운로드, 대시보드 정적 경로·CSP
- 기존 작업실·전체 흐름 프리뷰·실제 대시보드·예시 화면의 통합 빌드와 화면 이동
