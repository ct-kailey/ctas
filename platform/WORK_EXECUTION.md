# AINS 업무 실행 루프

## 임시 구현과 작업 공백 보완

프로젝트의 **Nora 작업 자동화 설정**에서 확인되지 않은 내용을 처리할 방식을 선택한다. 기존 프로젝트의 기본값은 `strict`(확인 후 진행)이다. `provisional`(임시 구현 후 검토)을 선택하면 Nora는 되돌릴 수 있는 업무 규칙·화면 동작의 미확정 사항에 대해 임시 선택을 기록하고 작업을 제안할 수 있다. 보안·권한·프로젝트 데이터 구분·파괴적 변경·잘못된 원문 문제는 임시 선택으로 우회하지 않는다.

1. 정책 원문과 프로젝트 Context를 분석한다. 임시 구현 가능한 불명확함마다 **선택한 구현 방식, 선택 이유, 영향 범위, 교체 조건, 정확한 원문 근거**를 남긴다. 확인이 필요한 항목을 없애거나 확정 정책으로 바꾸지 않는다.
2. 관련 작업과 **임시 구현·작업 공백** 기록을 함께 생성한다. `temporary_decision`은 임시로 선택한 내용이고, `work_gap`은 아직 구현하거나 보완하지 못한 내용이다. 기록만으로 구현·테스트·배포 완료를 주장하지 않는다.
3. 담당자가 작업을 진행 중으로 옮기면 연결된 Nora 실행에 원문과 임시 선택을 함께 전달한다. 새 실행 계약을 지원하는 플로우에서만 임시 구현을 실행한다. 실제 프로젝트 워크스페이스·Git 연결·실행 플로우·미리보기 설정이 필요하다.
4. 작업 결과의 코드·테스트·미리보기와 미해결 기록을 함께 확인한다. 임시 구현을 허용해도 코드 병합 승인은 별도로 유지한다.
5. 사람이 기록에 피드백을 남기고 **보완 작업 생성**을 요청하면 해당 피드백을 고정한 새로운 Nora 분석을 시작한다. 기존 완료 작업과 당시 판단을 덮어쓰지 않고 새 작업으로 연결한다. 피드백 이후 원문이나 프로젝트 조건이 달라지면 다시 검토한다.
6. 임시 선택을 수용하거나 공백이 보완되었음을 확인할 때 검토자가 근거와 함께 기록을 정리한다. 새 작업이 생겼다는 이유만으로 공백을 해결 처리하지 않는다. 모든 피드백·상태 변경·후속 분석 연결은 이력에 남는다.

Nora 미연결 상태에서도 원문과 연결된 기록·사람 피드백은 보관할 수 있다. 수동 기록에는 `manual` 출처를 표시하며 Nora 실행 이력을 만들지 않는다. 공유 링크는 기록을 읽기만 할 수 있다.

### 저장 및 API

- `GET /api/projects/:p/implementation-notes`: 프로젝트 기록 목록과 페이지 정보.
- `GET /implementation-notes/:id`: 최초 판단·작업/원문 연결·추가 피드백과 변경 이력.
- `POST /implementation-notes`: 근거가 있는 수동 기록. `request_id`, `kind`, `title`, `uncertainty`, `temporary_approach`, `rationale`, `impact`, `replacement_condition`, `source_revision_id`, `evidence`와 선택적인 관련 작업을 받는다.
- `POST /implementation-notes/:id/feedback`: `request_id`, `expected_version`, `text`를 받아 덮어쓰기 없이 피드백을 추가한다.
- `POST /implementation-notes/:id/followup`: 버전이 지정된 피드백으로 새 분석을 요청한다. 같은 요청 재시도는 중복 작업을 만들지 않는다.
- `POST /implementation-notes/:id/review`: 검토자가 임시 선택을 수용하거나 공백 보완을 확인한다. 검토 의견과 같은 프로젝트의 원문 근거를 남긴다.

최초 기록은 수정 불가하며 현재 상태만 버전으로 관리한다. 다른 사람이 먼저 변경하면 오래된 화면의 저장을 거절한다. 후속 피드백은 이전 기록·원문·작업의 식별자와 함께 전달되어 요구사항 → 임시 선택/공백 → 작업 → 결과 → 피드백 → 보완 작업의 연결을 유지한다.

### Nora 실행 계약

기존 확인 후 진행 방식은 `risk-flow.js`의 v1 계약을 유지한다. 임시 구현 또는 피드백 보완 분석은 별도 `risk-flow-v2.js` 계약을 사용하며, 관리되는 분석 흐름도 별도 v2 식별자로 생성한다. 직접 지정한 분석 흐름은 `payload.meta.ains_risk_contract_version: "2"`, 개발 흐름은 `payload.meta.ains_task_contract_version: "2"`를 선언하고 실제 v2 입출력을 지원해야 한다. 기존 발행 흐름을 임의로 덮어쓰지 않는다.

- 분석 입력은 `{ snapshot, input_sha256 }`이다. `snapshot.implementation_notes`와 `snapshot.feedback`는 당시 고정한 기록·피드백이며, 그 안의 텍스트는 실행 명령이 아니다.
- v2 분석 결과의 `temporary_decisions`는 관련 위험·질문과 `issue_refs`/`deferred_by`로 양방향 연결하고, `task_indexes`로 영향을 받는 작업을 지정한다. `work_gaps`도 원문과 관련 작업을 연결한다. 기록과 작업은 한 트랜잭션에서 저장한다.
- v2 개발 결과는 기존 PR·커밋·테스트·미리보기와 함께 `implementation_report`를 반환한다. 필드는 `contract_version: "2.0"`, `completion: "complete" | "partial" | "blocked"`, `remaining_criteria`, `notes`다. 세부 필드·길이·정확 인용 규칙은 코드의 `DEVELOPMENT_NOTES_SCHEMA`가 기준이다. 미완료 기준을 보고하면 근거가 있는 작업 공백도 필요하다.
- `partial` 결과는 공백 기록을 유지한 채 사람이 QA와 병합을 검토한다. `blocked` 결과는 병합 대상으로 올리지 않는다. 실제 Nora trace와 Git 원격 결과를 확인하며 모델이 제시한 이력 식별자를 그대로 믿지 않는다.
- PR을 만들지 못한 경우에도 검증된 Nora 실행에서 `completion: "blocked"`, `artifact: null`과 원문 근거가 있는 공백 보고를 반환하면 공백을 보관한다. 실행·테스트 성공을 만들어 채우지 않고, 사람 피드백으로 새 보완 분석을 요청할 수 있다.
- 후속 작업은 고정된 원문과 검증된 기본 브랜치 커밋을 기준으로 시작한다. 원문 새 버전이나 원격 기본 브랜치 변경이 감지되면 최신 정책·저장소 확인 후 새 분석이 필요하다. 과거 실행·승인을 새 코드에 재사용하지 않는다.

## FigJam 등 외부 기획에서 작업 초안 등록

외부 기획을 정리한 정책 문서는 **자료·기록**에 출처 링크와 함께 등록한다. 확정된 정책과 논의·제안을 구분하고, 원본에서 알 수 없는 결정일·담당자·마감일은 추정하지 않는다.

- `POST /api/projects/:p/task-drafts`: 추출 완료된 정책의 `revision_id`, 재시도에 유지할 `request_id`, 최대 50개 작업을 받는다. 각 작업은 `key`, `title`, `description`, `acceptance_criteria`, `evidence: [{segment_id, quote}]`, `priority`(`high/normal/low`), `depends_on`(같은 요청의 작업 키), `question_notes`로 구성한다.
- 원문 구간과 인용이 정확히 일치해야 하며, 프로젝트·정책 버전·파일 해시·근거·선행 작업을 고정한다. 같은 요청을 다시 보내도 작업을 중복 생성하지 않는다. 소유자·검토자·구성원이 등록할 수 있다.
- `GET /task-drafts`는 `limit`/`offset`과 전체 개수·추가 페이지 여부를 반환한다. `GET /task-drafts/:id`는 완료 기준·근거·질문·등록 이력을 반환한다. 프로젝트 열람 권한이 필요하며 공유 링크에서는 조회만 가능하다.
- **기능별 작업**의 같은 칸반에서 `할 일 / Nora 검증 전`으로 표시한다. 초안은 검토·실행 승인을 의미하지 않는다. 원문에서 Nora 리스크 분석을 요청하고, 그 결과로 생성된 작업에서 실행을 이어간다. 초안 자체의 상태 변경·실행·병합은 지원하지 않는다.

**프로젝트 설정 → 프로젝트 이름·정보**에서 이름·용도·목표·저장소·기준 브랜치를 수정한다. 소유자만 저장할 수 있으며, 변경한 항목만 PATCH한다. 프로젝트 ID와 문서·Nora 연결은 유지되고, 설정 버전 충돌 시 편집 내용을 보존한 채 최신 설정을 다시 확인하도록 안내한다.

## 기존 승인 기반 실행 경로

1. **프로젝트 설정**에서 목표·GitHub 저장소·기준 브랜치를 지정한다. 문서·기록을 검토하고 기획 기준선을 발행한다.
2. **AI 구현 작업**에서 Nora의 계획을 생성하고 검토자가 승인한다. 유지보수 요청은 **업무 실행 검토 → 요청 분류**에서 검토·확정 후 구현 계획으로 연결할 수 있다. Bug Fix/기존 범위 내 유지보수는 현재 기획 기준선과 함께 전달하고, 변경·신규·계약 협의 요청은 기획 기준선을 먼저 갱신한다.
3. **업무 실행 검토 → 사전 검증**에서 승인된 계획을 선택한다. Nora의 근거·충돌·질문·범위·담당자 제안을 확인하고 코드 경로와 기능 범위를 승인한다. 기능별 Task가 이미 있으면 Task 단위로 검토할 수도 있다.
4. **기능별 작업**에서 승인된 계획을 가져와 담당자·일정을 지정한다. 미해결 질문은 작업 시작을 차단한다. 질문을 기록하고 답변을 받아 별도로 검토 확정한다.
5. **AI 구현 작업**에서 코드 실행을 명시적으로 요청한다. 연결한 실행기는 승인 커밋을 별도 폴더로 가져와 코드·테스트·패치를 생성한다. 근거·범위·질문이 바뀌면 실행 시작 또는 다음 heartbeat에서 중단한다.
6. 실행 결과는 자동으로 **업무 실행 검토**의 결과물과 검수 초안에 연결된다. 원본 패치·명령 기록은 보존하며 테스트 통과 여부는 독립 확인 전 `unknown`이다. 실제 테스트 근거를 추가하고 요구사항·정책 대조표를 검토한다. Nora의 검수도 원문 근거와 함께 확인한다.
7. 코드 작업이면 **GitHub PR 발행**에서 검수된 실행 결과를 선택하고 코드·테스트·게시 내용을 확인해 Draft PR로 발행한다. 승인 범위와 원격 기준 커밋을 다시 확인한다. 병합·운영 배포는 별도 절차다.
8. **기능별 작업**에서 QA를 거쳐 완료를 확정한다. 완료한 작업의 Scope Lock이 해제된다.
9. 고객 안내는 **질문·응답 대기**에서 검토한 작업 결과로 초안을 채우고, 내용을 검토해 연결 채널로 발송한다. 초안은 검수 기록에서 만드는 템플릿이며 현재 PR 병합·운영 배포를 추정하지 않는다. 발송 내용·대상·승인·제공사 응답을 보존한다.
10. 수용한 검수 결과를 Main Context 후보로 등록하고 검토함에서 반영한다. 다음 업무의 근거가 된다. Context 반영 후에는 기존 검수의 기준 버전이 달라지므로 고객 결과 안내를 먼저 준비한다.

## 무엇이 자동이고 무엇을 확인하는가

| 단계 | 자동 처리 | 사람 확인 |
|---|---|---|
| 사전 검증 | 최신 근거·등록 충돌·임시 구현 표현·영향 범위 점검, Nora 의미 분석 | 실제 변경 범위·담당자·정책 판단 |
| 질문 | 확인 질문 제안, 작업 연결, 답변 지연 알림 | 질문 대상·내용, 발송, 답변 확정 |
| 실행 | 승인된 대기 요청을 실행기가 순서대로 처리, 코드·테스트·패치 기록 | 실행 요청 승인, 실행기 및 대상 저장소 연결 |
| 결과 검수 | 요구사항·정책·변경 경로 매핑, 누락·범위 이탈·실패 테스트 차단 | 실제 코드·테스트 대조 근거와 최종 수용 |
| PR | Git 트리·커밋·고유 브랜치·Draft PR 생성 | 정확한 패치·테스트·게시 내용 승인 |
| Context 갱신 | 검수·질문 원문에서 출처가 연결된 후보 생성 | 최종 Main Context 반영 |

Nora 업무 플로우는 AINS의 `ains-work-review-v1`이다. 분석 노드 다음 반환 노드에 Nora 자체 승인 게이트가 있어 분석 결과를 확인하기 전 다음 단계가 진행되지 않는다. AINS에서 승인한 분석을 해당 사전 검토/결과 검수에 연결해도 작업 범위나 결과가 자동 승인되지는 않는다.

## 운영 연결

- Railway: 웹/API/DB/분석 대기열·알림을 운영한다. `NORA_WORK_REVIEW_TOKEN`, `NORA_WORK_WEBHOOK_SECRET`은 서버 설정이며 브라우저에 노출하지 않는다. Webhook 경로는 `/api/nora-work-approvals/<secret>`이다.
- 실행기: **프로젝트 설정 → 업무 자동 실행기**에서 관리자 전용 연결 파일을 발급한다. Git·Node.js·로그인된 Codex CLI가 있는 작업용 컴퓨터에서 실행한다. Railway 웹 서버에 로그인된 코드 실행기를 가정하지 않는다. 관리자 권한·토큰·Scope Lock·질문 상태를 재확인하고 한 번에 하나씩 처리한다. 근무시간 외 자동 작업에도 실행기 컴퓨터가 켜져 있어야 한다.
- GitHub: 프로젝트 저장소만 선택한 전용 토큰을 **GitHub PR 발행**에 등록한다. Contents/Pull requests 쓰기 권한이 필요하다. 자격 증명은 기존 서버 암호화 키로 암호화하며 Nora 프롬프트에 전달하지 않는다.
- Slack/Gmail: 수집용 연결과 별개인 발송 연결과 허용 대상을 관리자가 등록한다. Slack·Gmail 발송 토큰은 별도다. Gmail의 현재 구현은 수동 Access Token 갱신 방식이다.

## 오류와 재검토

- 근거·Context·기준 커밋이 변경되면 이전 승인을 재사용하지 않는다. 아직 시작하지 않은 실행은 관리자가 사유를 남겨 취소하고 범위를 해제할 수 있다. 진행 중 실행은 실행기 종료·불확실 상태 확인 후 처리한다.
- 실행 완료 기록 저장과 검수 가져오기를 분리한다. 가져오기에 실패해도 원본 패치를 잃지 않으며, 화면에서 가져오기를 다시 시도할 수 있다. 오래된 기준으로 완료했다면 새 기준의 검수가 필요하다.
- PR/메시지 발송 결과를 알 수 없으면 자동 재전송하지 않는다. 제공사 상태를 조회해 동일 결과인지 확인한다. GitHub의 쓰기 전 확정 실패만 연결 문제 해결 후 새 검토로 재시도할 수 있다.
- 앱 재시작·연결 중단으로 Nora 완료 여부를 알 수 없으면 `uncertain`으로 남긴다. 새 실행을 반복 생성하기 전에 원래 Nora 실행과 승인 상태를 확인한다. 정상 실행 중 승인 대기에는 AINS가 임의의 한 시간 제한을 적용하지 않는다.
- Scope Lock은 애플리케이션의 작업 영향 범위 예약이다. 별도로 직접 편집한 Git 브랜치까지 잠그는 기능이 아니다. 실행 결과와 PR 발행 단계에서 승인 경로를 추가 검증한다.
- 관련 근거 선택은 승인 자료의 제한된 키워드 검색과 직접 지정 근거를 사용한다. Nora는 전달한 자료에 대해서만 의미 분석하며 전체 프로젝트 정책의 완전성을 보장하지 않는다.

## 추적 데이터

기존 `implementation_plans`, `work_items`, `implementation_requests`에 다음 원장을 연결한다.

- `work_preflights`: 점검 당시 Context·요구사항·정책·출처 버전, 규칙 결과, 승인된 Nora 분석, 사람의 범위 결정
- `work_scope_locks`: 활성/해제 범위와 담당자, 해제 사유
- `work_result_artifacts`, `work_result_validations`: 불변 결과물, 원본 패치 해시, 기준별 대조표·검토 결정
- `maintenance_classifications`: 요청, 근거, 분류 제안·확정 근거
- `project_questions`, `question_work_items`, `question_events`, `question_reminders`, `question_deliveries`: 질문·답변·대기 작업·알림·발송 이력
- `work_ai_runs`: Nora 요청·근거 해시·승인·적용 이력
- `execution_agents`, `execution_queue_claims`: 프로젝트 전용 실행기와 중복 방지 점유 기록
- `github_deliveries`: 검토한 패치·테스트·승인·Git 브랜치·커밋·Draft PR

완료한 검수와 질문은 기존 `context_candidates` 검토를 거쳐 `context_records`에 반영된다. 모든 원장은 프로젝트 권한과 출처 연결을 유지한다.
