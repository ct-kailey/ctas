# 계약·기획 문서 작성과 검토

신규 프로젝트 생성 후 **계약·기획**에서 시작한다. 고객 정보가 없는 새 프로젝트는 프로젝트·기업 정보 화면을 먼저 연다. 이 단계에 Git 저장소는 필요하지 않다.

## 사용 순서

1. **프로젝트·기업 정보**: 고객명, 기업 정보, 프로젝트 목표·범위, 일정, 예산·계약 조건, 확인 사항을 작성한다. 변경 근거를 함께 저장한다.
2. **사내 문서 양식**: 검토자가 제안서·견적서·계약서별 항목, 작성 지침, 회사명, 꼬리말을 등록한다. 참고 양식 원문은 문서 보관함에 업로드하고 추출이 완료된 버전을 연결한다. 기본 양식 3종은 반드시 **샘플**로 표시한다.
3. **계약 문서 → 문서 작성**: 문서 종류·양식을 선택한다. 직접 작성하거나 기존 업로드 원문에서 초안을 만든다. 본문 항목과 표를 편집하고 변경 내용을 적어 새 버전으로 저장한다. 나중에 문서 양식·원문 연결을 바꿔도 작성 본문은 유지된다.
4. **Nora로 양식 보정**: 저장된 최신 버전의 보정을 요청한다. 완료 후 원문·보정안, 변경 요약, 질문을 확인한다. **새 초안으로 적용**하면 별도 버전이 생긴다. 자동으로 승인되지 않는다.
5. **검토 결정**: 검토자가 최신 문서의 금액·일정·범위를 확인하고 승인하거나 반려한다. Nora가 필수 확인 질문을 남겼다면 내용을 보완하여 새 버전으로 저장한 뒤 승인한다.
6. **고객 협의 이력**: 실제 고객에게 전달한 요청 내용과 날짜·채널·문서 버전을 기록하고 답변을 추가한다. 프로젝트별 최대 2~3회이며, 대기 중인 답변이 있으면 다음 회차와 계약 확정을 막는다. 메시지는 자동 발송하지 않는다.
7. **단계 변경 → 계약 확정**: 내부 승인된 최신 계약서와 고객 합의 날짜·근거를 기록한다. 실제 전자서명 기능이 아니라 기존 고객 합의의 기록이다. 합의 근거와 과거 단계 변경은 화면에서 다시 조회할 수 있다.
8. **개발 인계**: 확정 계약을 검증하고 인계를 기록한다. **개발 설정**에서 Git 저장소와 브랜치를 연결한다. 구현에 사용할 요구사항을 문서 보관함에서 검토·기준선 발행한 뒤 **AI 구현 작업**에서 계획을 요청한다. 계약 확정만으로 코드가 실행되지 않는다.

## 파일 업로드와 출력

- 파일은 기존 보관함 업로드·추출 파이프라인으로 처리한다. 계약·기획에서 올리면 해당 화면으로 돌아와 추출 완료 후 원문을 선택할 수 있다.
- 업로드 원문은 통째로 보존하며, 연결 가능한 본문은 40,000자 이내다. 초과하면 조용히 자르지 않고 오류를 반환한다.
- DOCX/PDF에는 제목, 회사명, 본문 항목, 표, 버전, 승인 상태, 샘플 여부, 꼬리말과 페이지 번호를 출력한다.
- 항목 구조와 스타일을 적용하는 방식이다. 임의의 원본 DOCX 배치·로고·병합 표를 그대로 재현하지 않는다. 실제 사내 양식의 요구에 맞게 별도 조정할 수 있다.
- 다른 프로젝트 양식은 해당 프로젝트의 구성원인 경우에만 조회·복사할 수 있다. 항목·지침·회사명·꼬리말을 복사하며 참고 원문은 현재 프로젝트에 다시 등록한다.

## 권한과 이력

| 작업 | 관리자 | 검토자 | 실무자 | 열람자 |
|---|---|---|---|---|
| 정보·문서 작성, Nora 요청·적용, 고객 답변 기록 | 가능 | 가능 | 가능 | 불가 |
| 사내 양식 등록, 승인·반려, 진행 단계 변경 | 가능 | 가능 | 불가 | 불가 |
| 조회·DOCX/PDF 다운로드 | 가능 | 가능 | 가능 | 가능 |

프로젝트 생성 계정은 해당 프로젝트 관리자가 된다. 리드·영업 직책을 별도 전역 권한으로 만들지는 않는다.

- 문서 버전·양식·검토 결정은 덮어쓰지 않는다. 버전 변경에 사용한 양식 스냅샷을 보관한다.
- 문서와 프로젝트 버전을 함께 검증하여 검토 도중 조건이 바뀌면 승인을 거부한다.
- 프로젝트 정보 변경 시 기존 승인 유효성을 다시 확인한다. 확정 이후 문서·조건 변경은 고객 협의로 되돌리고 이전 확정 이력을 보존한다.
- 웹 화면은 계약 확정·개발 인계 상태에서 편집을 잠근다. 단계를 고객 협의로 바꾼 뒤 수정한다.
- 보정 요청은 정확한 문서 버전·프로젝트 정보·양식을 동결한다. 그 뒤 내용이 바뀌면 오래된 결과 적용을 막는다.
- 미저장 편집 내용을 버리는 화면 이동에는 확인 창을 표시한다. 저장 자체는 사용자가 명시적으로 한다.

## Nora 및 오류 처리

AINS의 `ains-commercial-drafting-v1` v2, OpenAI 모델을 사용한다. 입력·결과 스키마, manifest, 합성 수락 테스트는 `nora/commercial-drafting/`에 있다.

- 도구 호출·외부 탐색·메모리 사용 없이 형식과 문체를 보정한다.
- 문서 안 명령은 자료로 취급한다. 사내 양식 지침도 제한된 보정 목적에만 사용한다.
- 수치가 포함된 원문 줄, 일정·예산·고객명·명시적 계약 당사자, 원본 표를 검증한다. 위반 결과는 저장·적용하지 않는다. 의미 전체의 동일성은 사람이 대조한다.
- `failed`: 입력·연결 또는 보존 검증 오류를 확인한 뒤 사용자가 새 요청을 한다.
- `uncertain`: Nora 완료 여부를 확인하지 못한 상태다. 자동 재시도하지 않는다. 실행 이력 확인 후 필요할 때 새 요청한다.
- `409`: 다른 사용자가 문서·프로젝트를 변경했거나 보정안이 오래되었다. 최신 내용을 확인한 뒤 새 버전 또는 새 보정을 요청한다.

## 운영 구성

- `NORA_COMMERCIAL_TOKEN`: Railway의 서버 전용 변수. 로컬 개발은 권한 600인 `nora/.secrets/commercial-secret.json`을 사용할 수 있다.
- `platform/server/commercial-worker.js`: 한 요청씩 처리, HTTP 45초, DB lease 120초, 중복 전송 자동 재시도 없음.
- migration `012_commercial.sql`: `commercial_profiles`, `commercial_templates`, `commercial_documents`, `commercial_document_revisions`, `commercial_decisions`, `commercial_rewrites`, `commercial_feedback`; 일반 감사 기록은 `events`를 사용한다.
- `commercial-routes.js`는 `/api/projects/:project/commercial` 하위에 인증·구성원·CSRF·권한 검사를 적용한다.
- 출력은 Python `python-docx`·ReportLab과 NanumGothic을 사용한다. Docker에 폰트를 포함한다. 로컬 검증 시 의존성이 설치된 `PYTHON_BIN`을 지정한다.
