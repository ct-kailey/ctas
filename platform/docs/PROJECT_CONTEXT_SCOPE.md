# 프로젝트 자료와 구현 대상 구분

AINS 자체 제품을 개발하는 프로젝트와 AINS에서 관리하는 고객 프로젝트는 서로 다른 프로젝트로 등록한다. 프로젝트 이름에 AINS가 포함되어 있다는 사실이나 저장소 주소만으로 문서의 적용 대상을 결정하지 않는다.

## 프로젝트 경계

| 용도 | 포함할 자료 | 대상 저장소 |
| --- | --- | --- |
| 자체 제품 개발 | 해당 제품의 기획·기능·운영 요구사항 | 제품 코드 저장소 |
| 고객 프로젝트 | 해당 고객의 계약·업무 정책·요구사항·결정 이력 | 고객 시스템 코드 저장소 |
| 분류 필요 | 아직 용도를 확인하지 않은 기존 프로젝트 | 설정할 수 있으나 계획 생성 전에 용도 확정 필요 |

예를 들어 AINS 제품의 프로젝트별 접근 권한 요구사항과 고객 검사 시스템의 실험 선택 정책은 다른 프로젝트에 속한다. 제품 기획서에 고객 사례가 등장할 수 있으나, 사례의 업무 기능을 제품에 그대로 구현한다는 뜻은 아니다.

프로젝트별 문서·리비전·검색·검토·작업의 기존 접근 경계를 유지한다. 고객 자료를 제품 프로젝트로 복사해서 구현 근거로 삼지 않는다. 자료가 잘못 등록됐다면 원본과 이력을 보존하면서 올바른 프로젝트로 분리하고, 잘못된 자료로 생성한 이전 계획은 새 구현에 재사용하지 않는다.

## 개발 계획 생성

1. 프로젝트 설정에서 이름·용도·목표·대상 저장소·기준 브랜치를 확인한다.
2. 현재 프로젝트의 기획·요구사항 확정본을 선택한다.
3. **프로젝트·문서 적합성 확인**에서 목표·저장소·문서 원문을 대조한다.
4. 관리자 또는 검토자가 문서를 `구현 문서`, `참고 자료`, `다른 프로젝트 문서`로 판단하고 근거를 기록한다. 이 단계는 사람의 판단이며 자동 의미 분류가 아니다.
5. 미검토·참고·다른 프로젝트 문서가 있으면 계획 생성을 보류한다. 선택에서 제외하거나 올바른 프로젝트에서 처리한다.
6. 사용할 수 있는 문서만 남으면 요청자가 프로젝트·저장소·문서를 최종 확인하고 Nora에 계획을 요청한다.
7. Nora는 다시 목표와 문서의 업무 대상을 비교한다. 다른 대상의 요구사항이 섞이면 확인 질문과 범위 확인 작업만 반환하며 실제 구현 계획 승인을 막는다. AI 판정은 보조 검증으로 사용한다.

설정·저장소 상태·확정 문서·적용 대상 검토가 바뀌면 이전 확인으로 새 계획을 만들 수 없다. 최종 입력 확인은 확인한 사용자에게만 유효하며 30분 후 만료된다. 생성된 계획에 연결된 확인 이력은 보존하고, 이후 변경이 발생하면 승인·실행·실행기 착수 시에도 재검증한다.

## API와 저장 기록

- `project_settings.project_kind`: `product_development`, `client_project`, `unspecified`.
- `POST /api/projects/:p/implementation-source-reviews`: 관리자·검토자가 문서의 적용 대상을 기록한다. 정확한 리비전·내용 해시·프로젝트 설정 버전·저장소를 함께 고정한다.
- `POST /api/projects/:p/implementation-plan-preparations`: 현재 입력을 대조하고 `blocked` 또는 `ready`를 반환한다. 문서 미리보기와 보류 사유도 반환한다.
- `POST /api/projects/:p/implementation-plans`: 기존 입력에 `preparation_id`, `acknowledge_project_sources: true`가 필요하다. 다른 사용자·프로젝트의 확인이나 변경된 입력으로 우회할 수 없다.
- `implementation_source_reviews`, `implementation_plan_preparations`, `implementation_plan_confirmations`: 검토 근거와 최종 입력 확인을 변경 불가능한 이력으로 저장한다.

기존 계획의 원래 입력과 결과는 수정하지 않는다. 확인 절차가 없었던 이전 계획은 이력 조회용으로 남고, 새 절차에서 계획을 생성해야 승인·실행할 수 있다. 유지보수 분류에서 생성하는 계획도 동일한 절차를 따른다.
