# AINS platform MVP implementation contract

Node CommonJS + Express 5 API, React/Vite browser, PostgreSQL via pg. All application API responses JSON; errors `{error:{code,message}}`. IDs strings UUID, projects can have ASCII slug IDs. Browser never receives Nora tokens. Database raw document bytes (bytea, <=20 MiB) is deliberate initial private storage; future object-store adapter migration, not public uploads. Nora actual endpoints only, no silent mock fallbacks.

Auth: server local user accounts (scrypt), opaque hashed session token, HttpOnly SameSite=Lax Secure production cookie; DB sessions; CSRF double session token + exact configured Origin on mutations. Users provisioned by CLI; project roles owner/reviewer/member/viewer. No self signup. Project membership checked for every project route. Owner/reviewer publish or decide, member upload/review/answer, viewer read. Backend bootstrap env owner account only.

## HTTP contract (all project endpoints membership protected)
- POST /api/auth/login `{email,password}` -> `{user,csrfToken}`
- GET /api/session -> `{user,csrfToken}`; POST /api/auth/logout
- GET /api/projects -> `{projects:[{id,name,domain_pack,role}]}`
- POST /api/projects `{name,domain_pack?}` -> `{project}` (authenticated creates owner project)
- GET /api/projects/:p/overview -> `{documents,reviews,jobs,feed,counts,domains}`
- GET /api/projects/:p/documents -> `{documents}`; document `{id,title,baseline_revision_id,revisions:[{id,filename,status,sha256,created_at,error_code}]}`
- POST /api/projects/:p/documents multipart `file`, `title`, optional `document_id` -> `{document_id,revision_id,job_id}` (new revision immutable)
- GET /api/projects/:p/revisions/:r -> `{revision}` including document_json but NOT blob bytes
- GET /api/projects/:p/revisions/:r/original -> attachment binary, membership protected
- POST /api/projects/:p/revisions/:r/publish-initial `{reason,acknowledge_extraction:true}` -> `{baseline}` (reviewer, only if logical doc has no baseline; revision ready)
- POST /api/projects/:p/reviews `{revision_id}` -> `{review_id,job_id}`; current revision compared to currently published baseline, persist baseline snapshot; reject if no baseline or same revision. Deduplicate baseline/current pair.
- GET /api/projects/:p/reviews/:id -> `{review}` including result, request, answers, decision, job
- POST /api/projects/:p/reviews/:id/answers `{question_id,answer,evidence}` -> `{review}` (evidence text reference, no outbound send; pending review only)
- POST /api/projects/:p/reviews/:id/decision `{decision:'approved'|'rejected',reason,evidence,acknowledge_extraction:true}` -> `{review}` (reviewer; approved requires all questions answered with evidence, ready result, baseline unchanged; immutable decision pinned to request/result; reject does not require questions answered)
- POST /api/projects/:p/reviews/:id/publish `{reason}` -> `{baseline}` (reviewer; approved, baseline still equal snapshot; transaction updates document baseline and audit event; repeated identical publish idempotent)
- POST /api/projects/:p/jobs/:id/retry `{reason,acknowledge_duplicate_risk?:true}` -> `{job}` (member; failed retry; uncertain requires owner and explicit ack)
- GET /api/projects/:p/feed -> `{feed}` audit activity
- GET /healthz -> DB health only; no secrets.

Review object `{id,project_id,document_id,baseline_revision_id,current_revision_id,status:'queued'|'running'|'needs_review'|'no_change'|'blocked'|'failed'|'uncertain'|'approved'|'rejected'|'published',request,result,answers:[{question_id,answer,evidence,actor_id,created_at}],decision,created_at,job}`. Workflow job state is independent from business review result. UI never infers approval from no_change.

## Database ownership and worker interface
DB agent owns db.js (pool, migrate, transaction), migrations SQL, ledger.js business methods and ledger tests. Root owns auth.js/server.js and deployment. Worker agent owns worker.js/extractor.js + tests. UI agent owns platform/web entirely, no root package mutations. Root owns package.json dependencies/build scripts.

Required tables (DB agent final schema authoritative, communicate before drift): users(id,email,name,password_hash,created_at); sessions(token_hash,user_id,csrf_token,expires_at); projects(id,name,domain_pack jsonb,created_at); memberships(project_id,user_id,role); documents(id,project_id,title,baseline_revision_id,created_at); revisions(id,project_id,document_id,filename,mime_type,sha256,content bytea,status,document_json jsonb,error_code,created_by,created_at); reviews(id,project_id,document_id,baseline_revision_id,current_revision_id,request jsonb,result jsonb,status,decision jsonb,created_by,created_at); answers(review_id,question_id,answer,evidence,actor_id,created_at); jobs(id,project_id,kind:'intake'|'review',revision_id,review_id,status:'queued'|'running'|'succeeded'|'failed'|'uncertain',stage,stage_data jsonb,error_code,attempt,lease_token,lease_expires_at,created_at,updated_at); events(id,project_id,actor_id,kind,entity_id,detail jsonb,created_at).

DB methods may receive `{userId,role}` context resolved by root membership middleware. Export createLedger(pool); methods `listProjects(userId)`, `createProject(userId,{name,domain_pack})`, `listDocuments(projectId)`, `overview(projectId)`, `upload(projectId,userId,{filename,title,document_id,content})`, `getRevision(projectId,id,{includeContent=false})`, `publishInitial(projectId,id,userId,body)`, `createReview(projectId,userId,{revision_id})`, `getReview(projectId,id)`, `answerReview(projectId,id,userId,body)`, `decideReview(projectId,id,userId,body)`, `publishReview(projectId,id,userId,body)`, `retryJob(projectId,id,userId,body,role)`, `feed(projectId)`. Ledger must validate domain/business constraints, root validates authentication/roles. Ledger errors carry `code`, `status`.

Worker reads/writes pool using SQL, conditional lease_token commits, durable external call intent before any Nora request. Expired running job -> uncertain, never silent replay. Loop single in-flight job per instance, claim FOR UPDATE SKIP LOCKED and lease > upstream timeout, heartbeat; don't overwrite a newer attempt. Intake: extract temporary copy -> strict schema -> persist document+external intent -> runDocumentPipeline -> record normalized_document & run_id, ready. Review: stored immutable request -> runPublishedChangeReview -> validated output -> review status needs_review/no_change; no automatic decisions. Transport timeout unknown -> uncertain; completed HTTP error -> failed. On process crash completion unknown -> uncertain. Manual retry checked role+ack, same business record; revision snapshots always unchanged.

## Published registration suggestion contract

Nora workspace AINS (`t_ef2500ebb1b14058847dc513c5c197bc`) publishes `ains-record-registration-v1` version 1. One OpenAI `gpt-5.4-mini` agent uses `reasoning_effort: low`. Actual publication and agent IDs are recorded in [manifest.json](../../nora/registration/manifest.json). Five synthetic live API acceptance cases passed: same artifact revision, separate artifact in another domain, new conversation, instruction injection against selected domain, and filename-only input. Inspected traces showed no tool calls, memory reads or memory writes; these observations do not prove hard tool isolation.

`POST /api/projects/:p/registration-suggestions` requires owner/reviewer/member membership, session, CSRF and Origin checks. Body `{title,text,filename?,record_kind,domain_id?}`; the server constructs project-scoped domain/document candidates. The browser cannot supply candidate lists or override the trusted project context. Successful response `{status:'suggested',suggestion,trace_id,request_id,context,limitations}`; `suggestion` has exactly `{action:'new_document'|'new_revision',domain_id:string|null,document_id:string|null,record_kind,confidence,reason}`. The client validates selected domain, candidate ownership, unchanged record kind, exact agent output and successful execution. A suggestion does not create records, change baselines, approve work or start implementation.

Users explicitly apply a suggestion and separately submit registration. Candidate context is limited to 50 domains and 50 recent documents; text is limited to 20,000 characters. File-mode preflight uses title/filename without reading the file content. Empty text requires `new_document`, `document_id:null` and confidence <= 0.5. Unresolved business domain (`domain_id:null`) requires human confirmation of the selected domain. Normal file/editor registration limits remain separate.

The server requires `NORA_REGISTRATION_TOKEN` for classification; production never reads a local token file. Nora receives multipart `input` and `variables.registration_request`, with the raw trigger token in the `Authorization` header. Missing token or unpublished manifest yields `REGISTRATION_UNAVAILABLE` (503), while manual registration remains available. Railway activation requires the token and redeployment with the published manifest; live Nora acceptance is distinct from production platform verification, whose result is recorded separately in deployment evidence.

Before dispatch the server persists an input hash in `registration_requests`, with success/failure/uncertain completion and trace recorded afterward; the draft text itself is not stored in that table. Same-user concurrency 1, per-process concurrency 4, project quota 60/hour, platform timeout 45 seconds. Transport failures, aborted/timed-out response body reads and HTTP 5xx remain uncertain without automatic replay. Definite malformed JSON or invalid suggestion contracts fail closed. This advisory execution is separate from the `/jobs/:id/retry` workflow.

## Conversation collection and human inbox

Migrations 007/008 add four append-only provenance/review tables (`channel_sources`, `channel_events`, `channel_inbox`, `channel_batches`) and permit `discord`/`kakaotalk` in revision history. Current connection state is explicitly `not_connected`; there is no external webhook, channel authentication, background external watch, or message sender. Manual imports use existing session, Origin, CSRF and project permissions. Source preparation/pausing and accept/dismiss require reviewer/owner, intake requires member or above. Details: [CHANNEL_CONNECTORS.md](CHANNEL_CONNECTORS.md).

Source-scoped batch IDs and provider event IDs reject conflicting retries. Different batch IDs with the same evidence set share one inbox item while retaining immutable retry receipts. Known source timestamps order versions; equal/missing timestamps across competing versions remain ambiguous. Edits/deletions block stale acceptance; accepted document versions stay immutable and receive a provenance-change flag in the inbox. Source locking serializes intake against final review.

The published `ains-channel-triage-v1` uses one OpenAI `gpt-5.4-mini` agent. Validated output contains only classification, title, summary, record kind, confidence, nondeleted input evidence UUIDs, and reason. The PostgreSQL worker persists dispatch intent, published version and input hash before the call, uses a 120-second lease, and never automatically replays an uncertain execution. Missing token/publication switches to manual review with `TRIAGE_UNAVAILABLE`. Analysis success always requires human review. Approval here atomically creates a document/revision/intake job and records reviewer, reason, original evidence and whether AI analysis was absent; it neither approves a requirement nor publishes a baseline.

Six synthetic live Nora cases passed, including unconfirmed proposals, noise, prompt injection and deleted evidence. Traces showed no tool or memory use; hard tool isolation remains unproven. Full integration tests include PostgreSQL transaction/race, permissions, immutable evidence, idempotency and source-change cases. The production backup was restored into a separate local database; both migrations applied without changing data in any of the 15 existing tables. Evidence: [channel-backup-verification.json](../channel-backup-verification.json).

## Evidence-grounded implementation planning and separate execution

User workflow: **project settings → published specification baseline → Nora plan → human decision → explicit execution request → local runner → `patch_ready`**. See [IMPLEMENTATION_START.md](IMPLEMENTATION_START.md) for the UI, repository prerequisites and operator instructions. A document revision's `ready` means extraction/normalization completed; it does not authorize code execution. The currently supported execution target is a public GitHub HTTPS repository with a real branch and verified 40-character HEAD. An empty repository cannot be executed until initialized separately.

Migrations009/010 add `project_settings`, `implementation_plans`, `implementation_requests` and `implementation_runner_tokens`. Plans freeze the settings version, current published specification revisions, source hashes/segments and repository commit. Decisions freeze the reviewer, reason, input hash and result hash. Execution requests freeze the approved plan, sources, commit and explicit execution acknowledgement. Settings/baseline/commit changes block stale approval, execution and runner claims. Final decisions and execution results are immutable.

All paths below use `/api/projects/:p`, existing session/Origin/CSRF checks and membership:

| Endpoint | Contract |
| --- | --- |
| `GET/PATCH /settings` | `{settings}`; owner writes `{expected_version,goal,repository_url,base_branch}`. Configuration changes increment version and clear repository verification. |
| `POST /settings/verify-repository` | Server checks the fixed GitHub host and records `ready/empty/inaccessible/branch_missing`, verified HEAD and time; owner only. |
| `GET/POST /implementation-plans` | List `{plans}` or create `{request_id:UUID,revision_ids:[UUID]}` → 202 `{plan}`; member or above creates. Select 1–5 current published `specification` baselines, <=40,000 source characters. Same ID/same revisions replays the record; conflicting input is rejected. New plans limited to 20/project/hour. |
| `GET /implementation-plans/:id` | `{plan}`, including immutable input, result, trace, decision and computed stale reasons. |
| `POST /implementation-plans/:id/decision` | `{decision:'approved'|'rejected',reason,acknowledge_sources:true}` → `{plan}`; reviewer/owner. Approval requires fresh, validated `needs_review` result and no blocking questions. Resolve questions in goal/baseline and generate a new plan; there is no question-answer override API. |
| `POST /implementation-plans/:id/execution-requests` | `{acknowledge_code_execution:true,reason}` → 202 `{request}`; reviewer/owner, one request per approved plan. Repository must be ready and approval hashes must match. |
| `GET /implementation-requests`, `GET /implementation-requests/:id` | `{requests}` / `{request}` with status, immutable authorization, result and stale reasons. |
| `GET /implementation-requests/:id/patch` | Authenticated text attachment only after `patch_ready`; not a JSON response. |
| `GET /implementation-runner-script` | Owner-only executable script attachment. |
| `POST /implementation-requests/:id/runner-ticket` | Owner-only `{filename,ticket}`; ticket has schema version, origin, request ID, secret token and expiry. Valid for that one request for 2 hours; replacing it revokes the prior ticket. |
| `POST /implementation-requests/:id/revoke-runner-ticket` | Owner-only revocation while awaiting runner. Reissue/revoke cannot restart an already claimed request. |

Nora [manifest](../../nora/implementation-plan/manifest.json) identifies `ains-implementation-plan-v1` published v2, OpenAI `gpt-5.4-mini`/low. The strict [request](../../nora/implementation-plan/request.schema.json) and [result](../../nora/implementation-plan/result.schema.json) schemas allow only source-grounded planning data. Every task cites supplied revision/segment pairs; dependency IDs must be unique and acyclic. Exactly one published agent output must match final JSON. The flow does not inspect repository code, execute tools, or authorize work. Clear requirements leave code discovery to the later executor; empty/unverified repositories and missing business requirements retain blocking questions. Seven real synthetic cases passed, with zero observed tool/memory calls; [acceptance](../../nora/implementation-plan/acceptance-results.json) and [trace inspection](../../nora/implementation-plan/trace-inspection.json) are distinct from production verification.

`NORA_IMPLEMENTATION_TOKEN` is server-only. Requests use multipart `input` and `variables.implementation_request`, raw Authorization trigger token, 45-second timeout and no automatic retry. The worker claims one queued plan using `FOR UPDATE SKIP LOCKED`, persists version/input-hash dispatch intent, and uses a 120-second lease. Success becomes `needs_review`; missing token/publication becomes `failed/IMPLEMENTATION_UNAVAILABLE`. Expired running plans become `uncertain`, never silently replayed or approved.

The separate local [runner](../../scripts/run-implementation.js) calls `/api/implementation-runner/:id/{claim,heartbeat,complete}` with the single-request bearer ticket, not a browser session. The owner must still hold membership; expired/revoked tickets fail authentication. Claim grants a 3-minute lease, renewed every 30 seconds. Completion validates the lease, approved base commit, changed-file paths, patch hash and bounded result fields, and stores result plus audit atomically. Identical completion delivery is idempotent; this does not permit executing the request again.

The runner pins a disposable checkout to the approved commit, removes its Git remote, invokes the logged-in Codex CLI, and returns patch, changed files, reported checks, observed command exit codes and limitations. It does not push, create a PR, commit, merge or deploy. `patch_ready` is a reviewable code change, not proof of every acceptance criterion. Restart/lease expiry or an unconfirmed completion remains `uncertain`; preserve local `completion.json`, inspect server status and compare hashes before any new authorized request. These queues do not use `/jobs/:id/retry`. No automatic replay or manual success overwrite is provided.
