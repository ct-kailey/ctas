# 문서 등록에서 AI 구현 시작까지

## 과거 등록 문서 확인 기록

AINS SI·SM의 `Semi-auto 관련 정책`(리비전 `3bea3ace-6227-426c-b3d4-6a9cdb0f530b`)은 조회 당시 `ready`, 수집 작업은 `succeeded`였고 오류 코드는 없었다. 실제 Nora intake 실행 ID는 `897bb82b-8a40-4f6e-b10c-c61f74bafe46`이다. 최초 기준선도 이 리비전으로 발행되어 있다. 따라서 화면의 일반 안내 문구는 처리 실패를 뜻하지 않는다.

이 기록은 고객 프로젝트 자료를 사용한 과거 검증 기록이다. Semi-auto 정책은 AINS 제품 자체의 개발 요구사항이 아니므로 `ctas` 구현 계획의 근거로 사용하지 않는다. 제품 개발과 고객 프로젝트의 구분 및 새 계획 확인 절차는 [프로젝트 자료와 구현 대상 구분](./PROJECT_CONTEXT_SCOPE.md)을 따른다.

현재 intake는 파일/에디터 원문을 추출하고 구조를 검증·정리하는 파이프라인이다. 이 단계 자체는 LLM을 사용하지 않으며 코드·테스트·PR을 생성하지 않는다. AI 구현 계획은 별도의 Nora 플로우이며, 실제 코드는 별도 실행기가 작성한다.

| 기존 안내 코드 | 사용자에게 표시하는 의미 |
|---|---|
| CONTENT_IS_UNTRUSTED | 문서 안의 명령문은 자료로 보관하며 자동 실행하지 않음 |
| MOCK_DATA_UNVERIFIED | 예시 값과 실제 업무 값을 자동 구분할 수 없어 검토 필요 |
| 레이아웃·표·이미지 누락 가능 | 추출 한계 안내. 원문과 비교해야 하며 실제 실패 상태와 구분 |

화면은 일반 안내·내용 확인·추출 주의사항을 나누고, 기술 원문은 접힌 상세에 둔다. `ready`는 **추출·정리 완료**로 표시한다. 등록 직후 해당 리비전 상세가 열려 진행 상태와 다음 작업을 안내한다.

## 사용 순서

1. 프로젝트를 만들고 **프로젝트 설정**에서 이름·용도·목표, GitHub 저장소 URL, 기준 브랜치를 저장한다. 자체 제품 개발과 고객 프로젝트를 구분한다. **저장소 확인**은 실제 브랜치 커밋을 조회한다. 목표와 저장소 설정은 문서 등록과 독립적이지만 AI 작업 계획 전에 필요하다.
2. 기획 문서를 파일 또는 에디터로 등록한다. 추출이 완료되면 원문과 비교하고 최초 기준선을 발행한다. 후속 버전은 기존 변경 검토·승인·발행 절차로 기준선을 바꾼다.
3. **AI 구현 작업**에서 현재 발행된 기획 확정본을 선택하고 **프로젝트·문서 적합성 확인**을 진행한다. 관리자 또는 검토자가 구현에 사용할 문서인지 근거를 남겨 확인한 뒤, 요청자가 프로젝트 목표·저장소·문서를 함께 최종 확인한다. 미검토·참고·다른 프로젝트 문서는 제외해야 계획을 생성할 수 있다. 최대 5개 문서, 원문 합계 40,000자다. 초과 내용은 임의로 잘라 처리하지 않는다.
4. Nora가 작업 목록, 수용 기준, 기획 근거, 의존성, 확인 질문, 테스트 방향을 제안한다. 원문 근거를 검토한 사람이 승인하거나 반려한다. 구현을 막는 미확정 질문은 프로젝트 목표나 기획 기준선에 반영한 뒤 새 계획을 생성해야 한다.
5. 승인 후 별도로 **코드 실행 요청**을 한다. 실제 브랜치 커밋이 확인되어야 하며, 목표·저장소·기획 기준선이 바뀌었으면 새 계획이 필요하다.
6. 관리자가 **실행기 다운로드**와 **실행 연결 파일 받기**로 두 파일을 내려받는다. 연결 파일은 해당 요청 하나에만 유효하고 2시간 뒤 만료된다. 재발급하면 이전 파일은 취소된다.
7. Node.js 22 이상·Git·Codex CLI가 설치되고 Codex 로그인이 완료된 컴퓨터에서 실행한다.

```sh
node ains-implementation-runner.cjs --ticket ains-execution-실행요청ID.json
```

실행기는 연결 파일 권한을 소유자 전용으로 제한한다. macOS Codex 앱의 기본 CLI 경로를 사용한다. 다른 설치 환경에서는 `AINS_CODEX_BIN`으로 CLI 경로를 지정한다. 이 명령은 요청 하나만 처리하고 종료하며 상시 감시나 다른 프로젝트 실행을 시작하지 않는다.

8. 실행기가 실제 저장소 브랜치의 HEAD와 승인한 커밋의 일치를 확인하고 별도 임시 checkout에서 코드를 수정한다. 결과는 **변경안 준비됨** 상태로 저장된다. 변경 파일, AI가 보고한 검증, 실제 관찰한 명령·종료 코드, 제약사항, 패치를 확인한다.

승인한 계획은 **기능별 작업**에서 별도로 가져와 담당자·마감일·진행 상태를 관리할 수 있다. 담당자가 QA를 요청하면 검토자가 완료 기준과 결과를 확인하고 QA 근거를 남겨 완료 처리한다. 코드 변경안 생성만으로 작업이 완료되지는 않는다. [기능별 작업 관리 안내](WORK_ITEMS.md)를 참고한다.

현재 실행 범위는 코드 변경안 작성까지다. 원격 push·commit·PR·병합·운영 배포는 수행하지 않는다. 패치가 있다는 사실과 요구사항을 완전히 충족했다는 판단은 별개이며 최종 검토가 필요하다. 실행기는 Git 원격을 제거하고 변경 후 기준 commit·파일 경로·패치 해시를 검사한다. symlink, binary, 민감 파일명, 공백/비 ASCII 패치 경로 등 현재 검사기가 지원하지 않는 결과는 게시하지 않고 로컬 결과를 보존한다.

## 저장소가 비어 있는 경우

`ct-kailey/nora-flow`는 확인 당시 공개 저장소이며 default branch 설정은 `main`이지만 실제 브랜치/커밋은 없었다. 설정에 `main`을 적는 것만으로 기준 커밋이 생기지는 않는다. 이 경우 계획을 참고용으로 만들 수 있지만 초기 구성·기술 스택 등의 미확정 질문과 실행 차단 이유를 표시한다. 초기 코드가 있는 실제 업무 저장소를 지정하거나, 별도로 새 프로젝트를 초기화한 뒤 저장소를 다시 확인해야 한다. 이번 기능 구현은 해당 저장소를 초기화하거나 원격 파일을 수정하지 않는다.

## 구성과 DB

- Railway: 웹/API, 문서 처리기, 대화 분석 처리기, 구현 계획 처리기, PostgreSQL.
- Nora AINS: `ains-implementation-plan-v1`, OpenAI `gpt-5.4-mini`, 검토용 계획만 출력.
- 로컬 실행기: 승인 요청 1개를 받아 실제 Git checkout에서 Codex를 실행. Railway 웹 서비스에 셸 실행 API를 노출하지 않는다.

추가 테이블은 `project_settings`, `implementation_plans`, `implementation_requests`, `implementation_runner_tokens`다. 설정 버전·기획 기준선·원본/계획 해시·승인자/사유·저장소 commit을 불변 실행 snapshot으로 보존한다. 기존 문서/변경 검토 작업 테이블과 계획 큐를 분리했다.

일반 API는 세션·프로젝트 권한·Origin·CSRF 검사를 유지한다. 실행기 API는 요청 하나에 묶인 해시 저장 bearer credential만 사용하며 브라우저 쿠키로 접근할 수 없다. 관리자가 프로젝트 owner 권한을 잃거나 연결 파일이 만료/취소되면 실행기 접근도 차단한다.

계획 큐는 120초 임대, 실행기는 3분 임대와 30초 heartbeat를 사용한다. 프로세스 중단·임대 만료는 `uncertain`으로 보존하고 자동 재호출하지 않는다. 실행 중인 요청은 연결 파일 재발급으로 중복 시작할 수 없다. 종료 응답이 유실되면 로컬 `completion.json`을 유지하고 플랫폼 상태를 확인한다. 같은 작업을 자동으로 다시 실행하지 않는다.

## API 요약

모든 일반 경로는 `/api/projects/:p` 아래다.

- `GET/PATCH /settings`: 목표·저장소 설정, owner만 수정, `expected_version` 동시 수정 검사.
- `POST /settings/verify-repository`: GitHub 고정 호스트에서 실제 기준 커밋 확인. 공개 저장소 지원; 비공개 조회는 별도 읽기 인증 구성이 필요하다. 로컬 실행기는 현재 비대화형 공개 저장소 clone을 지원한다.
- `GET/POST /implementation-plans`: 계획 조회·요청, 요청 ID 재전송 중복 방지, 프로젝트당 새 계획 20개/시간.
- `GET /implementation-plans/:id`, `POST /:id/decision`: 계획 상세와 승인/반려.
- `POST /implementation-plans/:id/execution-requests`: 명시적 실행 요청. 승인된 계획당 1개.
- `GET /implementation-requests`, `GET /:id`, `GET /:id/patch`: 실행 상태와 변경안.
- `GET /implementation-runner-script`: 관리자용 실행기 파일 다운로드.
- `POST /implementation-requests/:id/runner-ticket`, `POST /:id/revoke-runner-ticket`: 단일 실행 연결 파일 발급/취소.
- `/api/implementation-runner/:id/{claim,heartbeat,complete}`: 단일 실행 credential 전용. 완료 결과와 감사 기록을 함께 저장한다.

실행기에는 플랫폼 토큰을 모델 환경 변수로 전달하지 않는다. 사용자 Codex 설정·MCP를 불러오지 않고 저장소의 `.codex` 설정도 별도로 보관한 뒤 복구한다. `workspace-write`와 네트워크 제한을 사용하지만, 이것을 모든 로컬 파일 읽기까지 차단하는 완전한 운영체제 격리로 보장하지 않는다. 상시 다중 사용자 실행기는 전용 계정/격리 환경으로 옮기는 것이 다음 배포 단계다.

공식 실행 방식: [Codex non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode).

## 카카오톡 시험 경계

‘대상’은 서비스 종류와 그 안의 정확한 대화방/채널을 함께 뜻한다. 첫 카카오톡 시험은 사용자가 지정한 방의 최근 대화를 1회 읽어 기존 수집·검토함으로 보내는 범위다. 방 이름이 아직 지정되지 않아 실제 대화는 읽지 않았다. 문서·기록 API, AI 계획, 로컬 코드 실행기와 독립적으로 진행할 수 있다.

카카오톡은 공식 채널 이벤트 API 대신 참고 스킬의 macOS 접근성 기반 읽기를 검토했다. Railway에서 Mac UI를 직접 실행할 수 없고 정확한 방 확인·원본 시각·중복/누락 검증이 필요하다. 부분 방 이름 매칭이나 다른 열린 창으로 대체하지 않는다. 실제 자동 watch는 1회 시험의 방·작성자·시각·원문 정확성을 확인한 뒤 별도 연결한다. ## 배포와 검증

2026-09-28 Railway 배포 `df7e380a-ac4d-43ee-a398-dfb9283a73c2`가 성공했다. 전체 테스트 406개, 실제 Nora 호출 7개가 통과했고 운영 DB 백업을 복원한 사본에 마이그레이션을 적용해 기존 19개 테이블 내용이 보존됨을 확인했다.

운영 환경의 별도 합성 프로젝트에서 에디터 기획 → 추출 → 기준선 → Nora 계획 → 승인 → 실제 Codex 실행 → 패치 저장·다운로드까지 검증했다. 공개 예제 저장소를 읽기 전용으로 clone해 `policy.js`, `policy.test.js`를 생성했고, 독립적인 Node 테스트와 네트워크를 차단한 Node 22 컨테이너 테스트도 통과했다. 고객 기획의 구현이나 원격 저장소 반영은 시작하지 않았다.
