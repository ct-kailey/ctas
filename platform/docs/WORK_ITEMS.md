# 기능별 작업 관리

승인한 Nora 구현 계획의 작업을 팀이 수행할 업무로 등록하고 담당자·마감일·진행 상태와 QA 근거를 관리한다. 승인된 계획과 원문 근거는 그대로 보존한다.

## 사용 순서

1. 기획 기준선을 바탕으로 Nora 구현 계획을 생성하고 검토·승인한다.
2. **기능별 작업 → 승인 계획 가져오기**에서 작업 범위를 확인하고 등록한다. 동일 계획을 다시 가져와도 작업이 중복 생성되지 않는다.
3. 관리자 또는 검토자가 담당자와 마감일을 지정한다. 해당 프로젝트의 관리자·검토자·실무자만 담당자가 될 수 있다.
4. 담당자는 작업을 진행·차단·QA 대기 상태로 바꾸면서 진행 내용과 막힌 이유를 기록한다.
5. 검토자가 완료 기준을 대조하고 QA 근거를 입력해 완료를 확정한다. 코드 변경안 생성 완료는 작업 완료로 자동 처리되지 않는다.

내 작업, 미배정, 기한 초과, QA 대기와 차단된 작업을 필터링할 수 있다. 마감일은 시간대 없는 날짜로 저장하며 기한 초과는 한국 시간(Asia/Seoul)의 오늘을 기준으로 판단한다. 오늘이 마감일인 작업은 기한 초과가 아니다.

## 상태와 검토

| 상태 | 의미 |
| --- | --- |
| 할 일 | 아직 시작하지 않은 작업 |
| 진행 중 | 선행 작업이 완료되어 착수한 작업 |
| 차단됨 | 해결할 사항이 있어 멈춘 작업. 차단 사유를 남긴다. |
| QA 대기 | 작업 결과를 완료 기준과 대조할 단계 |
| 완료 | 검토자가 QA 근거를 남기고 완료를 확정한 작업 |

선행 작업이 끝나지 않으면 진행·QA·완료로 넘어갈 수 없다. 기획 기준선이나 프로젝트 설정·저장소 기준이 바뀌면 재검토가 필요하다고 표시하며 새로 진행·QA·완료 처리하는 것을 막는다. 기록 추가와 차단 처리는 가능하다. 새 기준으로 계획을 다시 검토·승인한 후 새 작업을 등록하며, 이전 작업 이력은 남긴다.

모든 변경에는 사유가 필요하다. 담당자는 자신에게 배정된 작업의 진행 내용만 수정할 수 있으며 담당자·마감일 변경과 최종 완료는 관리자·검토자가 한다. 동시 수정 시 먼저 저장된 변경을 덮어쓰지 않고 최신 버전을 확인하도록 안내한다.

## 데이터와 API

`work_items`는 승인 계획·원래 작업 ID·작업 스냅샷·담당자·마감일·상태·차단 사유·버전을 저장한다. `work_item_events`는 변경 전후 내용, 작성자, 변경 사유, QA 근거와 기록 시각을 누적한다. 원래 작업에는 설명·수용 기준·원문 버전과 문단 근거·선행 작업 ID가 포함된다. 프로젝트 활동 기록에도 등록·변경 이벤트를 남긴다.

모든 경로는 `/api/projects/:p` 아래이며 프로젝트 접근 권한을 검사한다. 변경 요청에는 기존 세션·Origin·CSRF 검증이 적용된다.

- `GET /work-items`: 작업 목록과 배정 가능한 프로젝트 구성원 조회.
- `GET /work-items/:id`: 원문 근거·선행 작업·변경 이력을 포함한 상세 조회.
- `POST /implementation-plans/:id/work-items`: `{acknowledge_tasks:true}`로 승인 계획의 작업 등록.
- `PATCH /work-items/:id`: `expected_version`, 변경할 `status`, `assignee_id`, `due_on`, `blocker`, 필수 `note` 및 완료 시 `qa_evidence` 전달.

업무 등록과 코드 실행 요청은 각각 명시적으로 진행한다. 이 기능은 고객 질문 자동 발송, Slack 알림, 계약 체결, 자동 PR·병합·배포를 수행하지 않는다. 계약 전 기능 분석·고객 보충 요청 횟수 관리·기업 정보와 계약 검토는 후속 기능이며 저장소 설정 없이 시작할 수 있는 별도 기획 흐름으로 구성한다.
