# CTDS 전역 원칙

모든 CTDS 프롬프트 문서(축·토큰·컴포넌트·프리미티브·프리셋)의 상위 규칙.
개별 섹션 문서는 이 원칙을 다시 쓰지 않는다. 충돌 시 이 문서가 우선한다.

> **컴포넌트를 override·수정하기 전에 반드시 [OVERRIDE.md](./OVERRIDE.md)의 선행 체크리스트를 통과할 것.**
> 공통 컴포넌트에 이미 걸린 선언을 모른 채 로컬에서 덮으면 "이상한 지점에서 잘림·안 먹힘·오버플로우"가 반복된다.

---

## 1. 값과 판단의 분리

**토큰은 값을, 프롬프트는 판단을 담는다.**

- CSS 변수로 스왑되는 것: 프롬프트에 쓰지 않는다.
- AI가 "어떤 컴포넌트를 골라 어떻게 배치할지" 판단할 때 필요한 규칙: 프롬프트에 쓴다.

프롬프트에 등장 가능한 것: 토큰 이름(`space-6`), 축 이름(`density`), 축 값(`compact`), 컴포넌트 이름(`Button`), variant 이름(`primary`).
프롬프트에 등장 금지: 픽셀 값, 밀리초, 색상 hex/oklch 값, 폰트 이름.

---

## 2. 축을 먼저 존중한다

CTDS는 9개 축(Mode, Palette, Hue, Shape, Icon, Density, Motion, Font, Voice)으로 테마가 정의된다.
컴포넌트나 페이지를 만들 때, 먼저 **현재 축 값이 뭔지 확인**하고 그에 맞는 선택을 한다.

- 축 값을 무시한 하드코딩 금지 (예: density와 무관하게 항상 3열 그리드)
- 축 값에 따라 **컴포넌트 선택 자체가 바뀔 수 있음** (예: `density=comfortable`이면 테이블 대신 카드)
- 축 값을 알 수 없으면 프리셋 기본값 또는 `default` 값으로 가정

---

## 3. 프리셋은 시작점, 축은 오버라이드

프리셋(`gov-formal`, `startup-vivid` 등)은 9축 중 Theme이 묶는 6축(Mode/Shape/Icon/Density/Motion/Font)의 검증된 조합이다. Palette·Hue·Voice는 프리셋 밖에서 자유 선택.
사용자가 "gov-formal에서 shape만 soft로"처럼 지시하면, **프리셋을 기준으로 축을 부분 오버라이드**한다.

- 프리셋 이름이 있으면 그것으로 시작
- 개별 축 지시가 있으면 해당 축만 덮어씀
- 나머지 축은 프리셋 값 유지

---

## 4. 충돌 시 우선순위

여러 프롬프트 문서가 동시에 로드되어 규칙이 충돌할 때, 아래 순서로 위쪽이 이긴다.

1. **접근성 규칙** (§5 참고. `prefers-reduced-motion`, WCAG, 포커스)
2. **PRINCIPLES** (이 문서)
3. **컴포넌트별 `Don't`** (해당 컴포넌트 문서의 하드 리젝 규칙)
4. **축별 규칙** (Axis 문서의 Do/Don't)
5. **프리셋 기본값** (Preset 문서)
6. **사용자 지시** (프롬프트로 들어온 요청)

**해석 원칙:**
- 상위 규칙이 하위 규칙을 명시적으로 허용하는 경우엔 하위가 유효 (예: PRINCIPLES가 "축이 허용하는 예외"를 인정할 때)
- 사용자 지시가 접근성이나 PRINCIPLES를 어기려 할 땐 따르지 않고 사용자에게 확인 (§8 참고)
- 같은 계층 내 충돌은 §8에 따라 사용자에게 확인

### 4a. Don't 강도 레벨 (선택)

컴포넌트 `Don't` 블록 안에서 **강도 레벨**을 선택적으로 명시할 수 있다. 신규 Don't를 쓰거나 기존 Don't를 수정할 때 애매하면 아래 둘 중 하나를 bullet 맨 앞에 붙인다 — 명시가 없으면 "SOFT 수준으로 해석"이 기본 (사용자 지시로 깨도 됨).

- `[HARD]` — 어기면 CTDS 보증 밖. 사용자 지시가 요청해도 §8에 따라 **먼저 확인한다**. 예: "primary 2개 금지", "하드코딩 금지", "접근성 라벨 생략 금지".
- `[SOFT]` — 밀도·톤·관행 유지용. 사용자가 특별한 이유로 요청하면 따를 수 있고, 추후 되돌리기 쉬움. 예: "section 사이 gap은 space-6 선호".

레벨은 Don't에만 쓴다 (Do는 긍정형이라 레벨 불필요). AI는 신규 Don't 작성 시 **HARD인지 SOFT인지 애매하면 사용자에게 확인**하고 결정 — 임의로 HARD 안 붙임.

---

## 5. 접근성이 축보다 우선한다

- `prefers-reduced-motion: reduce` → `motion=none` 강제. Motion 축 설정을 무시한다.
- 색상 대비: `mode=high-contrast` 외에도 WCAG AA 미달 조합은 만들지 않는다.
- 키보드 포커스: 모든 인터랙티브 컴포넌트는 `ring` 토큰으로 포커스 표시.

접근성 규칙과 축 규칙이 충돌하면 접근성이 이긴다.

---

## 6. 하드코딩 금지

컴포넌트/템플릿 코드에서 다음은 하드코딩 금지 (프롬프트에서 이런 코드를 생성하지 않는다):

- 색상값 (hex, rgb, oklch 리터럴)
- 크기값 (px, rem, em) — 단, 1px border, 100% 등 구조적 값은 예외
- 시간값 (ms, s)
- 그림자 리터럴 (`box-shadow: 0 4px 12px ...`)
- 폰트 이름

모두 토큰 또는 CSS 변수를 경유한다. 하드코딩된 코드는 리뷰에서 거절한다.

**예외:** 축·프리미티브 문서의 "값" 또는 "축별 스왑" 표는 스펙 자체가 값이므로 허용된다.
예: Motion 축의 `expressive/standard/subtle/none`이 각각 어떤 duration/scale로 스왑되는지 명시하는 표.
이 값들은 CSS 변수 정의의 원본이지, 컴포넌트 코드에 하드코딩되는 리터럴이 아니다.
컴포넌트나 템플릿 코드에서 이 값을 리터럴로 쓰는 것은 여전히 금지.

**예외:** `Don't` 섹션에서 **부정 예시**로 리터럴을 인용하는 것은 허용된다.
예: "`#fff` 직접 지정 금지", "`font-family: "Pretendard"` 하드코딩 금지", "임의 정수(`9999` 등) 금지".
"이렇게 쓰지 마"를 보여주기 위한 인용이므로 리터럴 생성이 아니다.
단, 인용은 규칙당 1개로 최소화한다.

## 6a. 유령 토큰 금지

존재하지 않는 CSS 변수를 참조하는 것은 하드코딩보다 **더 위험하다** — 폴백 없이 `var(--없는-이름)`을 쓰면 브라우저가 상속된 base로 조용히 렌더해 사이즈·간격·색이 어긋나지만 **에러는 안 난다**. 그래서 리뷰에서도 쉽게 놓친다.

**규칙:** 각 토큰 문서의 "CSS 변수 whitelist"에 명시된 이름만 사용. 흔한 유령 접두어 — `--font-size-*`(실제는 `--text-*`), `--text-size-*`, `--fs-*`, `--spacing-*`(실제는 `--space-*`), `--duration-*` 외 임의 motion 이름.

**새 토큰이 필요하면:** 쓰지 말고, 먼저 토큰 문서와 globals.css에 정식 추가. 추측해서 쓰지 않는다.

---

## 7. 조합의 완성도 보증 범위

- **프리셋 조합**: 시각적 완성도 공식 보증
- **비프리셋 조합**: 동작은 하지만 완성도 미보증 — AI가 이런 조합으로 화면을 만들 땐 "비프리셋 조합입니다"를 사용자에게 알림
- **금지 조합**: 각 축·컴포넌트 문서의 `Don't`에 명시된 것 — 만들지 않는다

---

## 8. 애매할 때는 물어본다

프롬프트 규칙만으로 판단이 안 서면 임의 결정하지 않고 사용자에게 확인한다.
특히:

- 두 축 값 사이에서 어느 쪽 규칙을 우선할지 불명확할 때
- 컴포넌트 선택지가 여러 개이고 각각의 근거가 비슷할 때
- 프리셋이 지정되지 않았고 축 값도 부분적으로만 주어졌을 때

임의 판단으로 만든 화면은 재작업 비용이 크다. 확인 비용이 항상 더 싸다.

---

## 9. 언어

- 프롬프트 문서는 한국어로 쓴다 (팀 언어).
- 코드 식별자·토큰명·축명은 영어 (`space-6`, `data-density="compact"`).
- 컴포넌트가 화면에 표시하는 문구는 프로젝트별 `data-lang`을 따른다 — CTDS 프롬프트에는 화면 문구를 하드코딩하지 않는다.
