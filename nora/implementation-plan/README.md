# 구현 계획의 문서 적합성 확인

이 플로우는 고정된 문서 리비전과 프로젝트 목표로 **문서 기반 계획**을 작성한다. 저장소 URL·브랜치·커밋은 입력 식별 정보이며, 이 단계에서 저장소 코드를 조회하거나 다른 프로젝트 자료를 검색하지 않는다.

## 계획을 보류하는 경우

- 플랫폼 자체 개발 목표에 관리 대상 고객 프로젝트의 업무 요구사항이 선택된 경우
- 선택한 여러 문서 가운데 하나라도 별도 프로젝트의 구현 요구사항인 경우
- 자료가 예시나 참고 사례뿐이며 실제 개발 대상의 요구사항이 없는 경우
- 문서와 개발 대상의 관계가 불명확한 경우

보류 결과는 `blocking: true` 질문과 `TASK-1` 확인 작업 하나만 포함한다. 질문에는 확인할 문서 제목과 적용 대상의 차이를, 작업에는 실제 입력 리비전·문단 근거를 남긴다. 모델이 맞지 않는 문서를 임의로 제외한 뒤 나머지 문서의 구현 계획을 진행하면 안 된다.

플랫폼 명세 안에 고객 자료가 테스트 예시로 명시되고 플랫폼 기능과 예시의 관계가 설명된 경우에는 플랫폼 기능을 계획할 수 있다. 고객 도메인 용어가 등장한다는 이유만으로 차단하지 않으며, 고객 자료의 업무 규칙 자체를 플랫폼 기능으로 확대하지 않는다.

## 확실한 분리와 모델 판단의 역할

의미 판별은 보조 검증이며 완벽한 분류를 보장하지 않는다. 프로젝트·문서의 귀속 및 용도 확인, 대상 저장소 확인, 사람의 계획 검토와 서버의 승인 차단을 함께 사용해야 한다. 특히 목표가 모호하거나 문서에 다른 제품이라는 설명이 없으면 입력 자체의 분류를 먼저 바로잡아야 한다.

Nora 실행은 자동 세션을 사용하지 않고, 에이전트의 `forceFreshContext`를 켜며, 메모리·지식·외부 데이터·도구를 연결하지 않는다. 입력·출력 스키마와 기존 에이전트 ID는 유지한다.

## 회귀 확인

`acceptance-cases.json`에는 기존 일곱 경우와 다음 네 가지 대조 경우가 있다.

1. 플랫폼 목표 + 고객 제품 문서 → 보류
2. 플랫폼 문서 + 별도 고객 제품 문서 → 전체 보류
3. 플랫폼 접근 권한 명세 안의 고객 문서 예시 → 접근 권한 구현 허용
4. 고객 제품 목표 + 해당 고객 제품 문서 → 구현 허용

`node --test tests/implementation-plan-acceptance.test.js tests/implementation-client.test.js`는 입력·출력 계약 및 수용 검증기를 확인한다. 의미 분류 동작은 `IMPLEMENTATION_ALLOW_LIVE_NORA=1`을 명시해 실행하는 `run-acceptance.js`로 검증한다. `IMPLEMENTATION_SECRET_PATH`로 권한이 제한된 토큰 파일을 지정할 수 있다. 실 고객 문서를 수용 테스트에 사용하지 않는다.

특정 경우만 재현하려면 `IMPLEMENTATION_ACCEPTANCE_CASES`에 쉼표로 구분한 case ID를, 결과 보관 위치는 `IMPLEMENTATION_ACCEPTANCE_REPORT`에 지정한다. 2026-10-14 발행 버전 4에서 11개 합성 시나리오와 로컬 계약 검사 32개를 통과했고, 각 실행의 도구 호출·메모리 읽기·쓰기는 0이었다. Nora의 별도 사후 검증기(decomposition)는 백엔드 연결 오류를 반환했다. 따라서 위 결과는 AINS 수용 검증기의 확인 결과이며 Nora 사후 검증기의 성공을 뜻하지 않는다.
